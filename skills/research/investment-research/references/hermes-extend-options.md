# Hermes 扩展能力的方式对比

当用户想给 Hermes 添加新能力（如股票分析师、行业研究员、翻译助手）时，有几种不同的实现方式。选择合适的方案取决于资源、交互方式和维护成本。

---

## 三种方式对比

| 维度 | 同 Profile + 技能 | 独立 Profile + 同 Gateway | 独立 Profile + 独立 Gateway |
|------|:-:|:-:|:-:|
| **资源消耗** | 一个进程 | 两个进程（但1个gateway） | 两个进程 + 两个gateway |
| **飞书集成** | 一个Bot，同群同号 | 一个Bot，同群同号 | 两个Bot，要建群@不同号 |
| **记忆隔离** | ❌ 共享主记忆 | ✅ 完全隔离 | ✅ 完全隔离 |
| **模型可独立** | ❌ 共用 | ✅ 可不同 | ✅ 可不同 |
| **cron独立** | ✅ 主cron + 技能加载 | ✅ 各自cron | ✅ 各自cron |
| **你如何交互** | @一个号，我来分包 | @一个号，我调度子profile | @不同号或建群 |
| **维护成本** | 低 | 中 | 高 |

---

## 决策流程

```
要加新能力
  │
  ├→ 需要独立 cron 定时出报告？
  │   ├→ 是 → 独立 Profile（主 Profile 调 skill 也行，但 cron 记忆会混）
  │   └→ 否 → 继续
  │
  ├→ 记忆必须跟主身份严格隔离？
  │   ├→ 是 → 独立 Profile
  │   └→ 否 → 继续
  │
  ├→ 需要用不同模型 / Provider？
  │   ├→ 是 → 独立 Profile
  │   └→ 否 → 技能方案
  │
  ├→ 服务器资源够吗？（当前：1.8GB RAM）
  │   ├→ 紧 → 优先技能方案，不加额外进程
  │   └→ 松 → 可考虑独立 Profile
  │
  └→ 最终选择：
       ├→ 技能方案 — 日常交互通过我（元宝），需要时我加载技能处理
       ├→ 独立 Profile + 同 Gateway — 通过我 delegate_task 调用
       └→ 独立 Profile + 独立 Gateway — 建群双Bot @不同号
```

---

## 服务器环境约束

当前服务器：
- 内存：1.8GB
- 已运行：Hermes gateway + OpenViking + 膏方 Gunicorn + Nginx
- 每多加一个 gateway 进程约增加 200-500MB 内存

**结论：当前环境下，优先用技能方案。** 除非有明确需求（严格记忆隔离、独立模型）、且资源允许，才加独立 Profile + Gateway。
