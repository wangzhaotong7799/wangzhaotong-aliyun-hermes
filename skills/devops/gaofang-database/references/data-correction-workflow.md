# 数据修正（改库）工作流

主人让"把某几条数据的日期/状态改掉"时的标准流程（2026-08-27 实测）。

## 核心铁律：改库前必须先核对范围

**用户说的条数 ≠ date=某日的记录数。** 实例：主人说"刚导入的 5 条"，`date='2026-08-27'` 实际有 15 条，跨 3 个导入批次：
- 8.19 导入的 4 条（徐淑琴×2、祝端琦×2，单号 12420260818*）
- 8.27 00:59 导入的 10 条（张新龙/魏德珍/尚玉华/魏秀唤/李勤英，单号 12420260826*）
- 8.27 06:31 导入的 1 条（赵秋莲，单号 12420260819001）

正确做法：
1. 先 SELECT 按批次/患者分组列出候选（id + prescription_id + date + created_at）
2. 用 clarify 让主人确认精确范围，绝不擅自扩大/缩小
3. 主人澄清后目标日期可能**按批次不同**（本例：徐淑琴/祝端琦 4 条 → 8.19，赵秋莲 1 条 → 8.21）——别假设全部改同一个日期

## 改统计归属必须同步 created_at

月报按 `created_at` 统计（主人偏好口径）。**只改 date 不改 created_at，记录仍计入原导入月**，统计报表看不出变化。

created_at 是 timestamp，保留原时刻只换日期：

```sql
UPDATE prescription_records SET created_at = '2026-08-21 06:31:51.157392' WHERE id = 4488;
```

## 其他要点

- **date 与 created_at 可能已分离**：历史导入存在 date≠created_at 日期的情况（8.19 导入但 date=8.27）。核对时两个字段都看，别想当然认为它们一致
- 状态合法值：已取 / 已邮寄 / 未取 / 欠药 / 已退药（未取 = 未发放）
- 每步 UPDATE 后立即 SELECT 验证（id 列表 + date + status + created_at 全列）
- 案例：徐淑琴/祝端琦 4 条 created_at 本来就是 8.19（无需改），赵秋莲 created_at 从 8.27 改到 8.21——先核对现状，别多改
