# 🏗️ 团队架构师 — 多智能体团队组建SOP

> **什么是团队架构师？**
>
> 这不是某一个 agent，而是一套**标准化建队流程**。每次组建新团队前，必须先执行本SOP，把架构搭完整才能开工。
>
> **设计理念**：金脉小队(4人) + 星光小队(10人) + 影墨小队(3人) 的实践经验提炼。
> **核心原则**：架构优先、三大件完备、技能可叠加、记忆可沉淀。

---

## ⚖️ 铁律（不可违反）

| # | 铁律 | 说明 | 违反后果 |
|:-:|------|------|---------|
| 1 | **架构优先** | 任何 agent 开始工作前，必须完成完整目录/文件/角色架构 | 全部重来 |
| 2 | **三大件缺一不可** | 每个 agent 必须有 SKILL.md + SOUL.md + MEMORY.md | 缺一个就不算建好 |
| 3 | **记忆绝对独立** | 每个 agent 的 MEMORY.md 只能写自己的经验。严禁一个文件装多人记忆，严禁MEMORY.md互相引用 | agent记忆混淆→行为混乱 |
| 4 | **技能库先搭再工作** | scripts/ / references/ / templates/ 目录先创建，README写清楚用途 | 后续无法沉淀 |
| 4 | **铁律先行** | 每个 agent 的 SKILL.md 必须有自己的铁律（至少5条） | 行为失控 |
| 5 | **不编造记忆** | MEMORY.md 中的经验记录只能来自真实工作，不能伪造 | 误导后续迭代 |
| 6 | **一次建一个** | 逐个 agent 搭建，确保每个 agent 完整后再建下一个 | 防止遗漏 |
| 7 | **完整验收才能开工** | 全部 agent 搭建完毕后，跑完整验收清单，全部通过才允许工作 | 质量失控 |
| 8 | **所有操作必须请示** | 任何对系统配置、文件修改、外部操作的改动，必须先向主人询问经同意后方可执行。严禁擅自行动 | 任务无效+立即纠正 |

## 📋 团队组建全流程

### 阶段一：架构设计（先想清楚）

```
团队定位分析
    ↓
确定角色数量与分工
    ↓
绘制组织结构图
    ↓
定义角色间协作关系
    ↓
设计数据流转路径
```

#### 1.1 团队定位分析表

| 问题 | 答案举例（影墨小队） |
|------|-------------------|
| 这个团队解决什么问题？ | 视频提示词逆向工程 + 换产品翻拍 |
| 需要几个角色？ | 3个：帧捕手/画师/执笔 |
| 数据流向？ | 帧捕手→画师→执笔→交付 |
| 谁是总指挥？ | 影墨总指挥（orchestrator角色） |
| 输出给谁？ | Kling可灵→成品视频 |

#### 1.2 角色设计清单

每个角色回答以下问题：

```
□ 这个角色的核心职责是什么？
□ 他需要什么输入？
□ 他产出什么输出？
□ 他的数据/结果传给谁？
□ 他依赖哪些工具？
□ 他需要什么权限？
□ 他的性格定位（一句话概括）？
```

#### 1.3 组织结构图模板

```
┌─────────────────────────────────────────────┐
│            🎬 总指挥 (Orchestrator)           │
│         调度/协调/质量门/交付                 │
├──────────────────┬──────────────────────────┤
│                  │                          │
│     ↓ 委托       │       ↓ 委托              │
│  ┌─────────┐     │  ┌───────────┐           │
│  │ Agent A  │     │  │ Agent B   │  ...      │
│  │ (角色)   │     │  │ (角色)    │           │
│  └─────────┘     │  └───────────┘           │
│       ↓          │       ↓                   │
│  ┌─────────┐     │  ┌───────────┐           │
│  │ 输出到   │──┬──│→│ 输出到     │──┬──...   │
│  └─────────┘  │  │  └───────────┘  │        │
│               │  │                 │        │
│               └──┴─────────────────┘        │
│                        ↓                     │
│                 最终交付物                    │
└─────────────────────────────────────────────┘
```

#### 1.4 数据流转表

| 步骤 | 谁处理 | 输入 | 输出 | 传给谁 |
|:----:|:------:|:----:|:----:|:------:|
| 1 | Agent A | raw data | processed data | Agent B |
| 2 | Agent B | processed data | analysis result | Agent C |
| 3 | Agent C | analysis result | final output | 总指挥 |
| 4 | 总指挥 | final output | 核实+交付 | 用户 |

### 阶段二：创建目录结构

一个 N 人团队的标准文件结构：

```
~/.hermes/skills/multi-agent-team/
├── {team-name}-roster/           # 团队名册（全员档案表）
│   └── SKILL.md                  # 成员映射表、架构说明
├── agent-a/                      # Agent A
│   ├── SKILL.md                  # ✅ 技能定义 + 铁律
│   ├── SOUL.md                   # ✅ 灵魂档案（人格）
│   ├── MEMORY.md                 # ✅ 工作记忆（经验）
│   ├── scripts/                  # 脚本工具库
│   │   └── README.md             # 目录说明
│   ├── references/               # 参考知识库
│   │   └── README.md             # 目录说明
│   └── templates/                # 输出模板库
│       └── README.md             # 目录说明
├── agent-b/                      # Agent B（同上）
│   ├── SKILL.md
│   ├── SOUL.md
│   ├── MEMORY.md
│   ├── scripts/README.md
│   ├── references/README.md
│   └── templates/README.md
└── ...
```

**创建命令**（基线）：
```bash
BASE=~/.hermes/skills/multi-agent-team
TEAM={team-name}
AGENTS=("agent-a" "agent-b" "agent-c")

# 创建团队名册
mkdir -p $BASE/$TEAM-roster

# 逐个创建 agent 目录
for agent in "${AGENTS[@]}"; do
    mkdir -p $BASE/$agent/{scripts,references,templates}
    touch $BASE/$agent/{scripts,references,templates}/README.md
done
```

### 阶段三：逐个创建三大件（一次建一个）

#### 3.1 SKILL.md —— 技能定义 + 铁律

标准 YAML 前端：

```yaml
---
name: {agent-name}
description: {一句话描述}
version: 1.0.0
author: {团队名}
tags: [tag1, tag2, tag3]
toolsets_required: ['terminal', 'file', 'vision', 'web']
category: multi-agent-team
metadata:
  agent_type: specialist        # specialist / orchestrator / data_collector / report_writer
  team_role: {角色中文名}
  team: {团队名}
  priority: normal
  permission_level: read-write   # read-only / read-write
---
```

正文结构：
```
# {emoji} {昵称 EnglishName} — {角色名}

> **身份**: 一句话
> **座右铭**: 核心价值观

---

## ⚖️ 铁律（至少5条）

每条铁律规则：编号 + 一句话原则 + 简短解释

---

## 🎯 核心职责

2-4条核心职责，每句话一个职责

---

## 📋 SOP

工作流程（Step 1 → Step 2 → ...）

---

## ⚠️ 注意事项

已知坑点、故障排查、备选方案
```

#### 3.2 SOUL.md —— 灵魂档案

```yaml
---
name: {昵称 ({英文名})}
author: {团队名}
created: {YYYY-MM-DD}
version: 1.0.0
---
```

正文结构（4段）：

```
# {emoji} {昵称}的灵魂档案

## 一、名字寓意
- 中文名解析
- 英文名解析
- 合意
- 代号由来（一句话故事）

---

## 二、性格特质
5条特质 × 强度星级（★~★★★★★）+ 行为表现

---

## 三、说话风格
风格一句话概括
- 句式特征
- 常见表达
- 口头禅（3-4句）

---

## 四、座右铭
> **"..."**
```

**性格差异化原则**：
- 同团队内，每个 agent 的性格特质不重复
- 性格要呼应职能（技术型+1、审美型+1、交付型+1...）
- 铁律的严苛程度反映性格

#### 3.3 MEMORY.md —— 工作记忆

```yaml
---
name: {昵称 ({英文名})}
author: {团队名}
created: {YYYY-MM-DD}
version: 1.0.0
---
```

正文结构（必须从真实工作沉淀，不编造）：

```
# {emoji} {昵称}的工作记忆

## 一、基本信息
- 所属团队
- 上属（总指挥/哪个agent）
- 创建日期
- 关联配置（API Key、模型名、路径等）

---

## 二、已知项目背景
表格：项目名 / 输入 / 输出 / 状态

---

## 二·五、独立的技能库
表格：脚本库路径 / 参考库路径 / 模板库路径
迭代规则一句话

---

## 三、经验记录
- 踩过的坑（现象+原因+修复方法）
- 最佳实践（什么情况用什么方法）
- 有用参数记录

---

## 四、待办
- [ ] 待跟进事项（首次创建时从SOP中提取初始待办）
```

**记忆沉淀规则**：
1. **只记录真实体验** — 没做过的项目不写
2. **每次工作后更新** — 新发现的问题/优化/参数记录在本节
3. **记忆绝对独立** — 每个agent只维护自己的MEMORY.md。不共享一个文件写多人，不互相引用。你的经验只属于你
4. **定期清理已完成待办** — 已完成的事项移到「经验记录」
5. **失败比成功更重要** — 失败案例必须记录原因

### 阶段四：搭建独立技能库

每个 agent 的三个子目录用途：

| 目录 | 用途 | 存什么 | 迭代规则 |
|:----:|------|--------|---------|
| `scripts/` | 自动化脚本 | Python脚本、shell工具、API调用模板 | 每次发现新工具/新优化就加 |
| `references/` | 参考知识 | 参数表、案例库、资料索引 | 工作过程中需要参考的内容持续积累 |
| `templates/` | 输出模板 | 报告模板、文件格式、样式模板 | 新的输出格式要求出现时追加 |

**每个目录必须有的文件**：
- `README.md` — 目录说明、已有文件清单、新增规范

**README.md 模板**：
```markdown
# {emoji} {昵称} — {目录名}

> 一句话说明这个目录的用途

## 已有文件
| 文件 | 说明 | 依赖 |
|------|------|------|
| file.py | 功能说明 | 依赖列表 |

## 新增规范
- 格式要求
- 命名规则
```

### 阶段六：完整性验收（全部通过才能开工）

#### 6.1 单个 agent 验收清单

对**每个** agent 逐一检查：

```□ 通过 `skill_manage(action='create')` 正式注册到系统
□ 目录存在且完整（scripts/ references/ templates/ 均有）
□ SKILL.md 存在且有 YAML 前端
□ SKILL.md 有至少5条铁律
□ SKILL.md 有完整的 SOP（Step 1..N）
□ SOUL.md 存在且有4段完整内容
□ SOUL.md 的性格特质与职能呼应
□ MEMORY.md 存在且有4段完整内容
□ MEMORY.md 的经验记录是真实的（不含编造内容）
□ MEMORY.md 是独立的——不包含其他agent的经验，不被其他agent引用
□ 三个子目录各有 README.md
□ 角色定位明确（知道干什么、输入输出、数据流向）
□ 「所有操作必须请示」已写入铁律第8条
```

> ⚠️ **关键陷阱**：在 multi-agent-team 目录下放文件**不等于**在系统里注册了agent。
> 必须调用 `skill_manage(action='create', name='...')` 才会被Hermes系统识别。
> 2026-05-02的星光小队补全失败即因只建了文件没注册，导致系统重建后7人丢失。
```

```
□ 团队名册已创建（roster/SKILL.md）
□ 组织结构图已定义
□ 数据流转路径清晰
□ 每个 agent 的角色不重复
□ 总指挥角色已指定

### 阶段七：技能叠加与记忆沉淀（持续迭代）

#### 7.1 技能叠加规则

```
每次工作完成 → 每个agent自检
    ↓
有没有新发现的最优方法？      → 加入 scripts/ 或更新 SKILL.md SOP
有没有新发现的知识点？        → 加入 references/
有没有新的输出格式？          → 加入 templates/
有没有新的经验教训？          → 加入 MEMORY.md 经验记录
有没有新的工具依赖？          → 更新 README.md 依赖清单
```

**叠加原则**：
- 新技能不覆盖旧技能 —— 旧版本保留在脚本目录中，标注 `_v1` / `_v2`
- 每个 agent 的迭代不互相影响 —— 各自积累各自的
- 跨 agent 的升级由总指挥协调

#### 7.2 记忆沉淀规则

```
每次工作完成 → 更新 MEMORY.md
    ↓
已完成待办 → 移到「经验记录」
新发现的问题 → 加入「经验记录」（现象+原因+修复方法）
新项目信息 → 更新「已知项目背景」
新待办事项 → 加入「四、待办」
```

**记忆沉淀周期**：每次翻拍/项目完成，必须更新一次。不更新等于没做。

## ⚠️ 常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| agent 没有自我迭代 | MEMORY.md 没更新 | 每次工作后强制更新经验记录+待办 |
| 技能库越来越乱 | 脚本没有命名规范 | 按 `{功能}_{版本}.py` 格式，建新不覆盖旧 |
| 多个 agent 性格雷同 | 差异化没做好 | 重写 SOUL.md，按 技术/创作/交付 三型分配 |
| 总指挥不知道该找谁 | 名册没更新 | 更新 roster/SKILL.md 成员档案表 |
| 记忆文件编造经验 | 建队时偷懒 | 删除伪造记录，经验只能来自真实工作 |
| 新旧版本冲突 | 旧脚本被覆盖 | 建新文件不覆盖，原名加 `_v2` |

## 附录：跨队协作协议（Cross-Team Collaboration Protocol）

### 为什么需要跨队协作

各小队职能高度专业化，但工作流经常需要交叉：

| 场景 | 主力小队 | 需要协力的队 |

### 跨队调用规则

#### 规则一：可被外部调用的 agent 必须在 SKILL.md 中标注

在 SKILL.md 的 metadata 中添加 `external_accessible: true`，并在 SOP 中增加「对外服务接口」章节，写明：

- 自己能帮其他队做什么
- 请求格式是什么
- 返回格式是什么
- 限制和边界是什么

#### 规则二：调用方必须明确需求格式

请求跨队协助时，必须明确：

```
请求方: {小队名/agent名}
需求: {一句话说明需要什么}
输入: {提供给对方的素材}
输出格式: {需要对方返回什么格式}
紧急程度: {高/中/低}
```

#### 规则三：被调用方记录每次外部请求

每次完成跨队协作后，被调用方的 MEMORY.md 中要记录：

```
- 外部请求: {来自哪个队/哪个agent}
- 需求: {什么内容}
- 耗时: {多久完成}
- 经验: {这次协作为自己积累了哪些新知识}
```

#### 规则四：跨队调用不改变各自的数据流转主线

- 跨队调用是**旁路**，不影响主流程
- 天网在帮影墨小队采集数据的同时，仍然优先保证金脉小队的主任务
- 如果主任务排期冲突，由总指挥协调优先级

### 请求格式示例

```
📨 [天网请求]
   来自: 🎬 影墨小队·帧捕手
   需求: 采集抖音上婴儿水杯爆款视频的数据
   输入: 关键词 = ["婴儿水杯" "防漏吸管杯" "toddler cup"] 
   输出: 前10个热门视频的标题/点赞数/发布时间/视频链接
   紧急: 中
```

天网收到后回复：
```
📡 [天网回复]
   状态: ✅ 完成
   采集方法: sogou_direct + web_search(Tavily)
   耗时: 45秒
   结果: 10条记录已写入 ~/temp/cross_team_data_20260512.json
```

### 跨队调用后的记忆沉淀

每次跨队协作后：

**调用方（如帧捕手）** 在 MEMORY.md 中记录：
```
- 跨队协作: 调用了天网采集抖音爆款视频数据
- 结果: 获得10条记录，用于翻拍参考
- 评价: 天网用sogou_direct采集，速度快且命中率高
```

**被调用方（如天网）** 在 MEMORY.md 中记录：
```
- 外部请求: 来自影墨小队·帧捕手
- 需求: 抖音婴儿水杯爆款采集
- 耗时: 45秒
- 经验: 抖音母婴类内容用sogou_direct效果比baidu_direct好
```

这样**双方都从一次协作中积累了经验**，下次更快更好。
